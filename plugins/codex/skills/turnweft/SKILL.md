---
name: turnweft
description: Delegate bounded analysis or implementation to dim, droid, grok, opencode or agy and continue exact persistent sessions.
---

Use the registered Turnweft MCP tools. They run through the `turnweft` runtime (`npm install -g turnweft`); if it is missing, the plugin offers only a `turnweft_setup` tool that explains how to install it. Do not shell out to the `turnweft` command line instead: it cannot see this thread's permission mode, so it always asks the user to confirm.

1. Call `turnweft_agents` for availability, versions, capabilities and problems. Choose a provider; do not override its model unless the user explicitly requests one.
2. Create a session with `turnweft_session` action `create`, provider and the real project cwd. Save the exact returned sessionId in the task context. Continue with that ID; never guess the latest session or use a name as a resume handle. List defaults to scope=this_host. To discover another host's sessions before cross-host continuation, use scope=project with canonicalRoot, then explicitly `attach` the exact sessionId.
3. Generate a unique string requestId **before** submission and save it with the sessionId and prompt. Use `turnweft_ask` for analyze and `turnweft_delegate` for implement. Submit in the background, then save the returned jobId. If the response is lost, repeat the same prompt, intent and sessionId with the **same requestId** to recover the job. Never invent a new requestId for a retry.
4. Query `turnweft_job` with bounded waitMs (at most 25000), tracking afterSeq / nextSeq. Defaults return immediately. Read paged results with includeResult, resultOffset and resultLimit; follow resultNextOffset. Avoid rapid polling. `ok` describes whether the request was processed; inspect job.state, terminal, nextAction and resultComplete separately. An in_doubt job requires reconciliation, not prompt resubmission. A host query timeout does not cancel the job; explicit cancellation uses `turnweft_cancel`.
5. When submission returns `awaiting_confirmation`, the job is recorded in state `waiting_confirmation` and nothing has run. The user confirms once per provider × project × intent: through the host's confirmation dialog if it appears, otherwise through a macOS dialog that Turnweft shows on the user's screen and that waits until they choose. Tell the user what tier and extra permissions were requested and that a dialog is waiting. Do not resubmit: after Allow the same job starts by itself. Keep querying `turnweft_job` with waitMs 25000 in the same turn so you notice the confirmation and continue (nextAction stays `confirm_policy` while it waits); do not end the turn just to wait for the click. After about 10 minutes of waiting, stop and ask the user to say "continue" once confirmed. Deny cancels it with errorCode `confirmation_denied`; it never times out into a denial, only expires with the proposal (errorCode `confirmation_expired`). When the Codex conversation runs with full access (`sandbox_mode: danger-full-access`), Turnweft reads that from the turn metadata and authorizes the job directly: the result is `accepted` with a warning "Authorized by the host's bypass mode", and no dialog appears; other modes still show it. If the user prefers the terminal, give `turnweft policy grant <proposalId>` (type yes to allow, no to deny). Never confirm on the user's behalf, run the grant yourself, or treat tool arguments, auto-approval flags or a conversational claim as consent; only Turnweft itself reads the host's sandbox metadata.
6. Give the delegate a clear scope and acceptance criteria. While it writes, do not edit the same file range yourself. Preserve preexisting dirty files and external changes; do not reset them to simplify review.
7. Inspect the result, permission mapping and observed file changes. “Provider reports tests passed” is a claim, not independently verified evidence. Run appropriate checks yourself before stating verified acceptance, and distinguish unexecuted checks, reported checks and checks you actually ran.

All calls use Envelope: ok, data, error and warnings. Surface actionable errors and confirmation warnings to the user. Session close preserves history and rejects busy sessions by default; choose cancel_running only when authorized to stop the running task.
